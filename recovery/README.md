# haotian recovery data decryption

The built-in recovery starts `haotian-recovery-decryptd` with the QTI KeyMint and Gatekeeper HALs.
The daemon directly mounts the existing metadata-encrypted `/data`, installs the system and every
present user's DE key through the kernel fscrypt API, and then waits for optional per-user CE unlock
requests over a root-only local socket. Full Keystore2 and vold services are not included in
recovery. Users without a lock credential are unlocked automatically after DE becomes available.
This automatic storage unlock does not authorize ADB; the interactive authenticator must still be
entered after **Enable ADB**.

The QSEE, KeyMint and Gatekeeper executables and their private shared-library closure are packaged
in the dedicated recovery ramdisk. Recovery never mounts the `vendor`, `system`, `product` or `odm`
logical partitions for decryption. It only mounts the active-slot modem firmware partition
read-only, matching Qualcomm's existing recovery initialization, so an A/B OTA remains free to
write the inactive slot.

It is deliberately limited to the current Evolution X Gatekeeper Synthetic Password layout. It
does not support Weaver, enroll credentials, create replacement keys, format data, or migrate
userdata.

## Restricted recovery ADB

Haotian recovery may expose adbd's transport on a development build, but rejects every device-side
ADB service until **Enable ADB** is selected in the recovery UI. After that action, the only accepted
operation is an interactive `adb shell`, which starts the recovery authenticator instead of a
command shell. Until authentication succeeds, push/pull/sync, non-interactive shell commands, exec,
framebuffer, reboot, port forwarding and direct socket connections remain rejected.

The authenticator offers two independent paths:

1. The primary user's current lockscreen credential is verified by Gatekeeper and unlocks user 0
   CE. This authorizes full ADB and enters a shell in the same session. A secondary user's
   credential can decrypt that user's CE after ADB has been authorized, but cannot authorize ADB
   by itself.
2. ROM signing-key maintenance authentication authorizes full ADB without requiring DE or CE. The
   daemon generates a random 256-bit secret, encrypts it with every RSA OTA certificate in
   `/system/etc/security/otacerts.zip` using RSA-OAEP-SHA256, and displays the ciphertext and the
   SHA-256 fingerprint of its public key. Possession of a matching private signing key is proven by
   returning the decrypted secret as 64 hexadecimal characters.

For an Android signing key stored as an unencrypted DER PKCS#8 `.pk8` file, save the displayed
base64 ciphertext to `challenge.b64` and decrypt it on a trusted build machine with:

```text
base64 -d challenge.b64 | openssl pkeyutl -decrypt \
  -inkey releasekey.pk8 -keyform DER \
  -pkeyopt rsa_padding_mode:oaep \
  -pkeyopt rsa_oaep_md:sha256 \
  -pkeyopt rsa_mgf1_md:sha256 | xxd -p -c 256
```

`sign_target_files_apks --replace_ota_keys` rewrites the recovery copy of `otacerts.zip`, so a
release-signed target-files package automatically uses the release OTA key for maintenance
authentication. The AOSP testkey private key is public; challenges generated by an unsigned
development build provide no security and are only suitable for testing this flow.

Incorrect credential or maintenance responses use a daemon-wide exponential delay (1, 2, 4, 8,
... up to 300 seconds). The failure count and current deadline are stored in
`/metadata/ota/haotian_recovery_adb_auth_failures`, an existing recovery-writable metadata area, so
parallel shells and recovery reboots do not reset the delay. A successful authentication clears the
counter.

## ADB commands

While the gate is locked, start the only permitted ADB service and follow its menu:

```text
adb shell
```

The lower-level commands below are intended for a local recovery console, diagnostics after ADB has
already been authorized, or direct development testing with the gate disabled. Locked ADB rejects
these non-interactive shell commands.

Check the state:

```text
adb shell haotian-recovery-decrypt status
```

The status includes every discovered user ID, whether its DE and CE keys are installed, its stored
credential type, and whether it has a unified-profile credential file.

Unlock a device with no screen lock, a PIN, or a password:

```text
adb shell haotian-recovery-decrypt unlock none
adb shell haotian-recovery-decrypt unlock pin
adb shell haotian-recovery-decrypt unlock password
```

Use `--user` for a secondary full user or a profile with a separate lock challenge. For example,
to unlock user 10 with its own PIN:

```text
adb shell haotian-recovery-decrypt unlock --user 10 pin
```

No credential is stored in the recovery image or accepted on the command line; the prompt reads the
current credential from stdin with terminal echo disabled.

For a pattern, enter zero-based cell indexes in drawing order, separated by commas. Cells are
numbered from left to right and top to bottom. The grid size is read from `lock_pattern_size` in
`/data/system/locksettings.db`; the optional size is only a fallback if that setting cannot be read.
Evolution X sizes from 3x3 through 6x6 are accepted.

```text
adb shell haotian-recovery-decrypt unlock pattern
adb shell haotian-recovery-decrypt unlock pattern 6
adb shell haotian-recovery-decrypt unlock --user 10 pattern 6
```

For example, `0,1,2,8` means the first three cells of the top row followed by cell 8. The daemon
encodes each cell exactly as `LockPatternUtils.patternToByteArray(pattern, gridSize)` does, including
cell indexes 10 through 35 on 6x6 grids.

## Work profiles

A work profile with a separate challenge is handled like any other user and is unlocked with
`unlock --user USER_ID ...`. A work profile with a unified challenge has no user-entered credential
of its own. After user 0 is successfully unlocked, recovery reproduces the platform's current
`UnifiedProfilePasswordCrypto` flow: it obtains a fresh user-0 Gatekeeper authentication token from
the Synthetic Password, loads `profile_key_name_decrypt_USER_ID` from the LockSettings SELinux
Keystore2 namespace, decrypts the system-generated credential stored in
`/data/system/users/USER_ID/gatekeeper.profile.key`, and uses that credential to install the
profile's CE key. The generated profile credential is never logged or persisted by recovery.

This supports the current Evolution X profile format only. Recovery does not create profiles,
change separate-challenge policy, enroll credentials, or modify Keystore2 records.

## Touch input

Recovery packages the stock `xiaomi_touch.ko` and `synaptics_tcm2.ko` modules from vendor_dlkm in
the vendor ramdisk and loads them after their SPI, panel-notifier and Gunyah dependencies. The stock
firmware and `haotian_syna_thp_config.ini` are also copied into `/lib/firmware` in the recovery
ramdisk. Early init redirects `/odm/firmware` there for the stock library, so initializing touch
does not depend on mounting `odm` or another dynamic partition.

This controller uses Xiaomi's touch-host processing (THP) design. The kernel driver exposes raw
frames through `/dev/xiaomi-touch`; it does not produce usable input events by itself. The
`haotian-recovery-touch` service starts the same `libtouchreport` entry point as Xiaomi's stock
touchfeature service, using the stock HAL and primary algorithm libraries. The optional sensor and
second-algorithm libraries are deliberately omitted: the current firmware has no second algorithm,
and the sensor layer needs film/glove/water TensorFlow models that are unnecessary for recovery.

The THP process reports Type-B events through `Xiaomi_Touch_Input_0`. It reports X and Y in the
ranges 0..143999 and 0..319999 because the panel uses a super-resolution factor of 100. AOSP
Recovery reads those ranges with `EVIOCGABS` and scales them to the current framebuffer, so no
hard-coded coordinate translation is needed.
